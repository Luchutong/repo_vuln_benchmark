# 给当前 Agent 的迁移提示词：RepoVuln-50 v0.3.1 → v0.4.0

你需要把当前 RepoVuln-50 数据构建工作迁移到本包定义的 v0.4.0：**公报驱动、固定 SHA、静态根因定位、取消常规动态复现**。

## 目标

在新的工作目录/工作仓库中搭建 v0.4.0 工作流，并且只迁移新工作流实际需要的数据。旧工作目录只读保留，不能原地改写。不要把所有历史 draft 数据整体复制到新仓库。

## 第一步：只读盘点

1. 从实际数据目录统计仓库、快照、正式正样本、候选、位置、证据和费用记录数量；不要依赖聊天中历史数字。
2. 识别真正冻结的评测版本：优先要求 `evaluation_selection.decision_status=frozen`，且每个仓库恰好一个目标 SHA。
3. 对源数据文件计算 SHA-256。生成简洁盘点报告，但不要复制原始草稿到新工作仓库。

## 第二步：执行选择性迁移

使用本包 `scripts/migrate_selective.py`，先 dry-run，再检查迁移计划，最后写入新的空目录。默认迁移规则：

- 保留质量状态 PASS 的仓库元数据，以便继续完成 50 个仓库。
- 只迁移已经冻结的目标快照；没有冻结的仓库只进入 `selection_queue.jsonl`，不迁移其 proposed 快照和草稿漏洞标签。
- 只迁移目标 SHA 上已有 `confirmed_affected`、有可信公报 URL、且存在固定 SHA 源码 permalink 和根因位置的正式漏洞记录。
- 迁移这些正样本直接依赖的源码位置、相关 PASS 证据与状态行。
- 只迁移冻结目标快照对应的未解决/可能相关候选，以及有明确证据的快照级 triage 结果。与正式正样本别名重复的候选去重。
- 不迁移其他历史快照、与目标 SHA 无关的历史 CVE、旧全历史 `discovery_coverage`、全量旧 `reviews`、rejected/duplicate 且无相反快照级证据的候选、无关 evidence、原始 prompt/token 日志和 draft 报告。
- 对旧数据中已标为 `confirmed_affected`、但没有固定 SHA 源码定位或缺少公报来源的记录，不要直接复制为正式正样本；如来源信息足够，则转成一个精简的 `needs_static_location` 候选，否则只在迁移报告里计数并引用源 ID，不复制整条 draft。

## 第三步：静态验证新正样本

对迁入的既有正样本进行字段兼容性检查，而不是重新做动态验证。新收候选只按下列方式处理：

1. 权威公告确认受影响范围；
2. 将 release/tag 精确映射到目标 SHA；
3. 在目标 SHA 中确认公告所描述的根因操作/缺失检查；
4. 保存文件、函数/行范围、固定 SHA permalink、公告 URL 和一句判定理由。

默认不构建、不运行 PoC、不要求 fix commit。只有版本范围冲突、回溯补丁或根因不明确时，才查看最小相关 Diff。无法确定的样本保留 S3/unknown，不得为了成本而强行排除。

## 第四步：验证与报告

1. 执行 `python scripts/validate_dataset.py NEW_ROOT --draft`。
2. 运行全部合成测试。
3. 输出 `MIGRATION_REPORT.json`：源/目标每张表行数、迁移和排除计数、排除原因、源哈希、目标哈希、冻结快照数、正式正样本数、需要静态定位的候选数。
4. 报告必须明确：迁移不修改源数据；未冻结仓库只保留仓库元数据；旧历史/草稿表被有意省略；不能把迁移报告当成漏洞验证结果。
5. 不得自动冻结 proposed 版本、不生成虚假 `confirmed_affected`、不把 unknown 转为 confirmed_not_affected。

## 停止条件

完成新工作目录初始化、选择性迁移、校验与报告后先停下，等待审阅迁移报告；不要立即继续消耗大量 Token 扫描全部候选。只有确认迁移范围正确后，再按新工作流继续处理目标 SHA 上的候选。
