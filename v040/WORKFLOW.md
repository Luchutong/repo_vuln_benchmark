# RepoVuln-50 v0.4.0 工作流
## Advisory-Grounded Static Vulnerability Ground Truth

> 2026-10-30 修订：引入**公报可信度优先的快速准入**（T1/T2/T3）与**分层抽样复核**。高可信公报直接采信漏洞身份、类型、触发条件和严重程度；每条样本只独立核对「评测 SHA 是否受影响」和「源码位置」两个事实。修订不改变已迁移数据的事实，只改变后续准入与复核方式。

## 0. 目标与边界

最终测试对象是**只接触一个固定 commit 源码**的代码审计 Agent。因此，数据集应尽可能收集并标注该 SHA 上公开已知的漏洞，而不是证明每条 CVE 都能在本地运行触发。

**正式正样本的最低可信条件：**
1. 有高可信公报或权威漏洞记录（官方维护者公告、厂商安全公告、GitHub Reviewed Advisory、NVD/OSV 记录）；
2. 受影响版本范围与选定 SHA/release 有明确可追溯关联；
3. 在选定 SHA 的源码中定位到与公报描述一致的组件、函数或危险操作；
4. 无已知反证：公告撤回、目标 SHA 前已有回溯修复、或版本范围冲突。

常规流程**不要求**：完整攻击链复现、本地 PoC、编译运行、动态红绿测试、穷尽历史 Git commit、为每条漏洞找到 fix commit、逐条双人独立复核。

要区分两件事：

- **高 Stars 仓库**只说明项目知名度，不能证明某条 CVE 的真实性，也不能降低证据要求；Stars 只用于仓库筛选。
- **高可信漏洞公告**（官方维护者公告、GitHub Reviewed Advisory、有明确 affected range 与修复说明的厂商披露）才是降低验证成本的依据。

不宣称 Ground Truth 是该版本全部真实漏洞的封闭全集。报告应表述为“在冻结日期前，经指定来源检索并完成静态核验的已知漏洞”。

### 0.1 两个正交维度

| 维度 | 取值 | 含义 |
|---|---|---|
| 准入等级 `advisory_trust_tier` | T1 / T2 / T3 | 这条漏洞走了哪条准入路径，是否进入正式 Ground Truth |
| 证据等级 `evidence_level` | S1 / S2 / S3 | 该条目的静态证据强度 |

T1/T2/T3 是**路由**，S1/S2/S3 是**证据强度**，不要把两者混用。候选记录一律为 T3。

## 1. 固定评测目标

- 每个仓库恰好一个冻结评测 SHA；优先选官方 release/tag 指向的 commit，减少版本映射成本。
- 记录仓库 URL、repo_id、SHA、tag/release、发布日期、全量语言清单和源码范围。
- Agent 评测输入只含该 SHA 的源码及必要构建信息，不含 `.git` 历史、漏洞公报、修复 Diff、Ground Truth 或答案标签。
- 只有 `evaluation_selection.decision_status=frozen` 的选择会迁入新工作集。未冻结仓库可保留合格仓库元数据并进入选择队列，但不迁入其 draft 快照/漏洞标签。

## 2. 漏洞发现：以公报为入口

对每个固定仓库/SHA，优先检索：
1. 上游项目 Security Advisories / 官方安全公告 / 厂商安全页面；
2. GitHub Advisory Database、OSV；
3. NVD/CVE 记录及公报引用的研究资料；
4. 仅在公告缺少定位信息时，追踪公告直接引用的修复 PR/commit。

按 CVE/GHSA/OSV 别名去重。同一漏洞多条公告合并为一个漏洞实体，保留所有来源。不要遍历全部历史提交来“猜”漏洞，也不要为不影响目标 SHA 的历史漏洞重建完整档案。

### 2.1 公报可信度优先的快速准入（T1/T2/T3）

| 等级 | 定义 | 处理方式 | 是否进入正式 GT |
|---|---|---|---|
| **T1：直接采信公报** | 官方维护者公告、厂商安全公告、GitHub **Reviewed** Advisory；受影响版本与目标 release 明确一致 | 只做 3 项自动检查（见 3.1），不做额外独立研究 | 是，S2；若同时确认修复前危险逻辑则为 S1 |
| **T2：定向静态核查** | 公报可信，但存在版本分支歧义、源码定位不清、或来源为 NVD/OSV/带权威引用的第三方记录 | 只检查相关 Diff、函数和必要调用者；不重做完整漏洞研究 | 定位成功且版本关系明确 → S2；否则 S3/候选 |
| **T3：保留候选** | 未经审核的第三方记录、版本范围冲突，或来源不可信且无法定位源码 | 写入 `candidates`，保留理由与来源 | 否，不计入评分分母 |

**Reviewed vs Unreviewed GHSA：** GitHub Advisory Database 中存在未经 GitHub 复核的条目。只有明确标记为 Reviewed 的 GHSA，或仓库自行发布的安全公告，才可按 T1 处理；Unreviewed GHSA 按 T2/T3 处理，并在 `advisory_review_status` 中记录。不得仅凭 GHSA 编号存在就视为已审核。

**OSV 范围解析：** affected range 必须按对应生态与 Git 分支语义解析（introduced/fixed/last_affected、semver/PEP 440/Maven/Go module 等），不能只比较版本字符串。存在 backport/cherry-pick、分支回合并或区间跨版本时，转入局部源码检查，不能凭 SemVer 字符串下结论。

### 2.2 采信边界

对 T1 公报，**直接采信**：CVE/GHSA 身份、漏洞类型与描述、CWE、CVSS/严重程度、公报给出的触发条件与影响范围。**只独立核对**：

1. 评测 SHA 是否落在公告覆盖的版本/分支范围内；
2. 目标 SHA 中是否存在公告描述的组件、函数或危险操作。

其余字段（fix commit、PoC、测试、完整利用路径）均为可选佐证。公报未提供的值不得由模型编造。

## 3. 验证方式：静态优先、分层核查

### 3.1 T1 的三项自动检查

对 T1 样本，最低只做以下三项，全部通过即可按 S2 入库：

1. **SHA ↔ release 对应**：评测 SHA 确实对应公告覆盖的发布版本；若是 tag 之间的 commit、存在 backport 或分支回合并，则不能走 T1，转 T2。
2. **组件/函数存在**：公告点名的组件、函数或危险操作确实存在于该 SHA；保存文件、函数/行范围、固定 SHA permalink 和一句根因说明。
3. **无反证**：公告未撤回；目标 SHA 之前没有已知回溯修复；没有与公告冲突的版本区间。

三项均通过且公报说明足够具体 → **S2**；若还确认了修复前的具体危险逻辑（例如最小 Diff 或等价安全检查对照）→ 可升 **S1**。

若公告只声明“整个项目受影响”，没有可靠源码位置，则只能生成**版本级标签**（`location_scope=version_only`），不得参加源码定位评分；存在性与版本级 Recall 仍可统计。

#### 3.1.1 批量走快速通道时的附加约束

`promote_from_proposals.py` 把上述三项检查落成可审计的机械规则，以下两条是实践中新发现的边界：

- **公报正文必须点名定位文件。** release 合并提交经常一次携带多个公报的修复，同一个 commit 的 diff 里混着若干 CVE 的 hunk。若只用“被删行仍存在于冻结树”来选位置，会把 A 公报的位置落到 B 公报的代码上。规则：公报 `details`/引用中提到带目录的文件路径时，定位文件必须与其一致；公报没有点名文件时，只有当该 fix commit 不被同仓库其他公报同时引用，才允许使用。
- **同一公报在同一快照下只产生一条漏洞行。** CVE/GHSA/生态别名会各自形成候选行；同一 canonical 公报（优先 GHSA id）的其余候选写成 `duplicate`，并用 `canonical_candidate_id` 指向主行，而不是各生成一条漏洞。

这两条只影响“位置选得对不对”和“行数会不会重复”，不改变 S1/S2 的判定口径。

### 3.2 T2 的定向静态核查

只查看公告/修复 Diff 直接涉及的文件、函数和必要调用者，确认：

- 文件/函数确实存在于目标 SHA；
- 公报描述的危险操作或缺失安全检查确实能在目标源码中定位；
- 没有明显的等价修复、权限检查、输入校验或上游保护使原描述不适用；
- 源码 permalink 指向固定 SHA，而不是可变的 `main`/`master`。

无需重新完整推导攻击链。触发前置条件和利用路径可复用公报，但必须与目标源码的危险操作对应起来。若只找到同名函数、文件或模块，不能认定根因已确认。

### 3.3 修复提交的使用边界

有官方 fix commit 时，优先查看与根因直接相关的最小 Diff，帮助理解漏洞代码和修复代码的差异。没有 fix commit 不阻塞入库。`fix_commits`、`fixed_releases`、CVSS 向量、PoC 和测试链接均为可选字段；官方未提供的值不得由模型编造。

### 3.4 动态复现

不要求本地 PoC、编译、运行或动态红绿测试。S1/S2 只表示静态证据充分，不表示动态利用已成功。

## 4. Ground Truth 等级

- **S1 — 高置信静态真值**：T1/T2 准入 + 目标 SHA 明确受影响 + 目标源码根因定位 + 独立静态佐证（例如直接修复 Diff、官方测试或等价安全检查对照）。
- **S2 — 可接受静态真值**：T1 三项检查通过，或 T2 定向静态核查完成；版本关系与根因代码明确。触发条件/路径可引用公报，不要求独立复现。
- **S3 — 候选，不进入主评分分母**：公告可信但版本关系、根因位置或源码对应关系仍不明确；或来源为 Unreviewed/第三方且未完成定向核查。

| 准入等级 | 典型结果 |
|---|---|
| T1 | S2（默认）；确认危险逻辑时 S1 |
| T2 | 定向核查通过 → S2；未通过 → S3/候选 |
| T3 | S3/候选，不进入正式 GT |

S1/S2 可成为正式 known-positive；S3 保留在候选队列。S1/S2 不代表漏洞已动态复现。

## 5. 状态规则

- `confirmed_affected`：权威来源支持版本关联，且目标 SHA 静态代码支持根因。
- `confirmed_not_affected`：有可靠的版本/分支/代码证据证明目标 SHA 不受影响，或存在等价修复。不能只凭“找不到代码”就下阴性结论。
- `possible_affected`：公告范围命中，但源码根因尚未确认。
- `unknown`：来源冲突、版本映射不明、无法定位或无法排除回溯修复。
- `duplicate` / `out_of_scope`：有别名/范围依据，不能用来掩盖分析困难。

不确定时保留 S3/unknown，不允许为节约成本将它强行改成阴性。也不需要为了把每个候选变成确定结论而无限消耗 Token。

候选是否解决以 `snapshot_candidate_triage` 的决策为准：`confirmed_affected` / `confirmed_not_affected` / `duplicate` / `out_of_scope` 视为已解决，`possible_affected` / `unknown` / 无 triage 行仍属未决。删除候选行不算解决；候选行保留，决策与证据单独成行。版本解析优先用 OSV 的 `versions` 与 SEMVER/ECOSYSTEM 区间，其次用 NVD 2.0 年度 feed 的 CPE 配置（`versionStart*` / `versionEnd*`）。只有 GIT 区间、无包名的记录、或裸 `*` 版本条目不足以判定版本关系，保留 `unknown`。`confirmed_not_affected` 必须有明确的上游区间/CPE 排除或等价修复证据。

## 6. 字段与缺失值

- `advisory_trust_tier`：`T1`/`T2`/`T3`，记录该条目的准入路径。
- `advisory_review_status`：`github_reviewed`/`vendor_official`/`unreviewed`/`unknown`，记录公报来源是否经过审核。
- `admission_checks`：T1 三项自动检查的布尔结果（`sha_release_match`、`component_present`、`no_counter_evidence`）与备注。
- `location_scope`（status 表）：`source_location` 或 `version_only`；只有前者参加源码定位评分。
- CWE、严重程度、CVSS：直接引用公报/可信数据库并保存来源。缺失写 `null`/`unknown`，不编造。
- 严重程度冲突：漏洞存在性仍可确认，但 severity 维度标记 `conflict`/不可评分。
- 修复版本/commit：尽力从公报取得；缺失不阻塞静态 Ground Truth。
- 位置：至少有文件路径、固定 SHA permalink、函数或行范围之一，以及根因说明。S2 默认允许函数级位置；只有标注行号有可靠依据时才做行级评分。

## 7. 成本控制

1. 先用脚本完成别名去重、官方数据提取、版本范围解析、SHA/tag 映射和文件/函数搜索。
2. **T1：只跑三项自动检查**，不重复阅读公告已给出的漏洞研究，不重建攻击链。
3. **T2：只读公告/修复 Diff 指定的最小代码范围**；只有找不到根因时才查看相关调用者。
4. **T3：不继续消耗模型调用**，保留候选并写清阻塞原因。
5. 缓存公告、版本范围解析、Diff、固定 SHA 源码定位和模型结果；按仓库/候选/阶段记录 Token 与实际费用。
6. 预算到达软阈值时只处理高优先级相关候选；达到硬阈值停止新模型调用并保存检查点。未接入调用网关前，成本脚本只能汇总，不能真正拦截请求。

## 8. 选择性迁移规则

迁移工具默认只复制：
- 质量状态 PASS 的仓库元数据；
- 具有 `evaluation_selection.decision_status=frozen` 的唯一目标快照；
- 该快照上已有 `confirmed_affected`、且有公报 URL 和固定 SHA 静态根因位置的漏洞；
- 这些正样本直接关联的源码位置、必要 PASS 证据和状态行；
- 冻结快照对应的 active/unknown/possible 候选及有证据的快照级排除结果。

默认不复制：
- 未冻结的 proposed 快照与对应 draft 标签；
- 其他历史快照和不属于评测 SHA 的漏洞记录；
- 全部旧 `reviews.jsonl`（旧 A/B 门槛不再作为新流程必需条件）；
- 旧全历史 `discovery_coverage.jsonl`（不能证明新快照覆盖）；
- rejected/duplicate 且没有相反的快照级证据的候选；
- 与已迁移正样本无关的证据、原始模型 Prompt/调用日志和历史草稿报告。

源数据保持不变。迁移报告记录每张表的源/目标行数、跳过原因、源文件哈希。迁移后未冻结仓库只进入 `selection_queue.jsonl`；不会自动把 proposed 记录升级为 frozen。

**Tier 回溯标注不是重新验证。** 迁移后的正样本按公报来源和既有检查结果标注 T1/T2/T3；标注脚本（`assign_trust_tiers.py`）只读已有字段，不访问网络、不重新判定漏洞真实性，并生成独立报告记录 before/after 哈希。

## 9. 评测与发布

- **存在性 Recall** = 命中的 confirmed_affected 数 / 该 SHA 的 S1/S2 known-positive 数。
- **源码定位 Recall** = 命中的、且 `location_scope=source_location` 的 known-positive 数 / 同口径分母。
- `version_only` 条目只进入存在性/版本级统计，不进入源码定位评分，并单独报告数量。
- 按仓库 macro recall 汇总，并分别报告 CWE、语言、严重程度、定位粒度和 **T1/T2 分层**。
- 行级定位仅对具有可信行号的条目评分；函数级标签使用函数级匹配规则。
- Agent 未匹配的发现进入独立裁决；未决发现不自动视为 FP。
- `PASS_KNOWN_SWEEP` 只表示针对冻结 SHA 的来源检索闭环，不等于穷尽所有真实漏洞。

发布前每个目标正样本必须有公报来源、固定 SHA 根因位置（或明确标注 `version_only`）、S1/S2 证据级别与 T1/T2 准入等级；未解决的可能相关候选必须被披露。任何未解决的相关候选存在时，不得宣称 Ground Truth 完全覆盖。

## 10. 抽样复核（替代逐条双人审核）

不再要求每条漏洞由两个 Agent 独立复核。采用**自动准入 + 分层抽样复核**：

1. **随机抽样**：对 T1 样本按 10%–20% 抽样（初始 15%），按仓库/语言/CWE 分层；抽样用固定随机种子，结果写入 `qa_reviews.jsonl`，可重复。
2. **强制全查**（不受抽样比例限制）：
   - 版本范围冲突或 backport 歧义；
   - 多个 CVE/GHSA 共用同一代码位置（别名或定位碰撞）；
   - 公报与源码明显不一致；
   - `version_only` 且被用于存在性统计的条目。
3. **抽样结果**：`pass` 直接保留；`fail` 必须追溯同一 stratum 的相邻样本，并决定降级（T2/T3）、修正或升级复核。
4. **报告**：发布报告写明抽样比例、样本量、分层方式、错误率；抽样比例按实际错误率调整。
5. **边界**：抽样复核只校验“版本关系 + 源码位置 + 无反证”，不要求重做漏洞研究或动态复现。

详见 `docs/REVIEW_SAMPLING.md`。
