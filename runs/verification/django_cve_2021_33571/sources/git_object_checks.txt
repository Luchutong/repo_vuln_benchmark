Vulnerable code at 3.0.2 (validators.py, blob 2e00ca3f):
    64  class URLValidator(RegexValidator):
    ...
    78      # IP patterns
    79      ipv4_re = r'(?:25[0-5]|2[0-4]\d|[0-1]?\d?\d)(?:\.(?:25[0-5]|2[0-4]\d|[0-1]?\d?\d)){3}'
    80      ipv6_re = r'\[[0-9a-f:\.]+\]'
  The octet alternative `[0-1]?\d?\d` matches one to three digits and therefore
  accepts octets with leading zeros such as 000, 016, 01, 002. A URL such as
  http://016.016.016.016/ is therefore a valid URL under URLValidator, even
  though many resolvers interpret a leading-zero octet as octal (016 -> 14),
  so an access-control decision taken by parsing the dotted string can
  disagree with the address the client actually connects to. That mismatch is
  what the CVE calls "indeterminate SSRF, RFI, and LFI".
  The same missing restriction exists in the standalone validators:
   252  def validate_ipv4_address(value):
   253      try:
   254          ipaddress.IPv4Address(value)
   255      except ValueError:
   256          raise ValidationError(_('Enter a valid IPv4 address.'), code='invalid')
  On Python < 3.9.5 ipaddress.IPv4Address also accepts leading-zero octets; the
  fix adds an explicit octet check (lines 252-... below). validate_ipv46_address
  at 264-269 calls validate_ipv4_address and inherits the same behaviour.
  This dossier's location is the URLValidator.ipv4_re line 79, the pattern that
  admits leading-zero octets into URLs; the two functions are named in the same
  fix and are described here for completeness.
