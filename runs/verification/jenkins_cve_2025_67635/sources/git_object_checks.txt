  Three of the four exit paths call side.handleClose(); the IOException path
  (157-158), which is the one taken for a corrupted stream (e.g. the
  "corrupt stream: negative frame length" IOException thrown at line 136, or any
  IOException from the socket), returns without notifying the side. On the server
  the side is the CLI session: CLIAction's run() blocks in
   274        void run() throws IOException, InterruptedException {
   275            synchronized (this) {
   276                while (!ready) {
   277                    wait();
   278                }
  and `ready` is set by ready() (269-272), called by onStart() (247-249) when the
  START frame has been parsed and by handleClose() (261-267). With handleClose()
  skipped, a stream corrupted before the START frame never wakes the command
  thread, and the
  paired upload request in FullDuplexHttpService.upload() also waits forever:
   144        // wait until we are done
   145        while (!completed) {
   146            wait();
   147        }
  because `completed` is set in the finally of the download handler's run(...)
  (FullDuplexHttpService.java 118-124), which is stuck in CLIAction.run. The
  connection is established without authentication (FullDuplexHttpService.Response
  168-170: "do not require any permission to establish a CLI connection"), so an
  unauthenticated client can open cli?remoting=false connections and corrupt the
  stream, holding request-handling threads and their connections indefinitely;
  repeating this exhausts the HTTP thread pool (denial of service). The class
  comment at CONNECTION_TIMEOUT (line 71, 15 s) shows timeouts were already used
  elsewhere in this class (the download-side wait at 104-116), but not on these
  two waits.
  The admission race is a second defect fixed by the same commit: CLIAction kept
  its pending connections in `new HashMap<>()` (field duplexServices), which is
  mutated concurrently from request threads; the fix switches it to
  ConcurrentHashMap and the regression test drives 50 concurrent CLI clients to
  provoke the uncaught exception. This dossier's location and claim are the
  indefinite wait / missing close above, which is what the CVE description names.
