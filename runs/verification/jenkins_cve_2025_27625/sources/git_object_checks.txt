Vulnerable code at 2.441 (Util.java, blob 24b04ce3):
  isSafeToRedirectTo at 1658-1660 is
    return !isAbsoluteUri(uri) && !uri.startsWith("//");
  It treats a value starting with a backslash (single or double) as safe.
  isAbsoluteUri (1646-1652) only rejects strings with a ':' before '#', '?' or '/',
  so "\example.org" and "\\example.org" pass both checks.
  Callers that send redirects based on this predicate:
  - DirectoryBrowserSupport.serveFile (blob 6f8bf2e6), lines 205-209:
      String pattern = req.getParameter("pattern");                  (205)
      pattern = req.getParameter("path");  // legacy                (207)
      if (pattern != null && Util.isSafeToRedirectTo(pattern)) {      (208)
          rsp.sendRedirect2(pattern);                                 (209)
    where pattern comes from the request.
  - AuthenticationSuccessHandler.determineTargetUrl (blob a5c7cffc), lines 42-55:
    returns originalTargetUrl at 52-53 when isSafeToRedirectTo(originalTargetUrl), i.e. a
    login "from"/original target starting with a backslash is accepted.
  - ParametersDefinitionProperty line 180 (redirectTo form field) uses the same
    predicate to decide whether to redirect.

  The patch changes the predicate to
    return !isAbsoluteUri(uri) && !uri.startsWith("\\") && !uri.replace('\\', '/').startsWith("//");
  so any leading backslash is rejected and backslash-slash mixes are normalised
  before the "//" check. It adds core/src/test/java/hudson/UtilTest.java cases
  ("\\\\google.com", "\\/google.com", "/\\google.com", "\\google.com") and the new
  test/src/test/java/jenkins/security/Security3501Test.java, which drives
  userContent?path=<encoded backslash variants> and expects a redirect to the
  local userContent/ directory instead of the attacker host.
