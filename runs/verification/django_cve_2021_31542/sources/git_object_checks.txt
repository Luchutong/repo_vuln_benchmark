Vulnerable code at the snapshot (3.0.2):
  django/core/files/uploadedfile.py UploadedFile._set_name (lines 38-50):
    line 42  name = os.path.basename(name)
  os.path.basename removes directory prefixes but returns '.' and '..'
  unchanged, and on POSIX does not treat '\' as a separator.  The method has no
  rejection for empty names or dot segments, and no later check exists in
  3.0.2: django/core/files/utils.py (blob de896071) contains only
  FileProxyMixin, there is no validate_file_name.
  django/http/multipartparser.py in 3.0.2 has no sanitize_file_name; it only has
  IE_sanitize (lines 300-302) which strips up to the last backslash.
  django/core/files/storage.py generate_filename (lines 101-108) calls
  os.path.normpath(os.path.join(dirname, ...)) with no dot-segment check.
  A multipart part with filename "." or ".." therefore survives as the stored
  UploadedFile.name and reaches the storage layer as a path segment.

Fixed code at 3.1.9:
  django/core/files/utils.py validate_file_name (lines 6-14) rejects names that
  are not their own basename and rejects '', '.', '..'.
  django/core/files/uploadedfile.py _set_name calls validate_file_name(name) at
  line 51.
  django/core/files/storage.py adds pathlib.PurePath(dir_name).parts '..' checks
  in get_available_name and generate_filename.
  django/http/multipartparser.py replaces IE_sanitize with sanitize_file_name,
  which strips both '/' and '\' and returns None for '', '.', '..'.
  The 3.1.9 release notes state: "MultiPartParser, UploadedFile, and FieldFile
  allowed directory-traversal via uploaded files with suitably crafted file
  names ... empty file names and paths with dot segments will be rejected."
